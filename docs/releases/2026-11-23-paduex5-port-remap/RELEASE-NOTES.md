# 五键固件 V3.5：5 号口损坏时，第 5 键改接到 6～9 号口之一（2026-11-23）

**仅限 5 号口损坏的五键板，正常板不要刷。** 四份文件上报的版本都是 V3.5，区别只在第 5 键接哪一个口。以文件名和 SHA-256 区分，不要只看上位机左上角的版本号。

分支 `feature/paduex5-port6`（base：`main`）。四键固件、普通五键固件、上位机都不改。

| 文件 | SHA-256 | 第 5 键接到 |
|---|---|---|
| `PADUEX5_P6_V3.5.bin` | `b62e07e812408cf4e5dde3896650ba618609177807203eac51108cb7e0fa0ef3` | 口 6：SCL PB3，SDA PB4，灯 PC9 |
| `PADUEX5_P7_V3.5.bin` | `81fba5b2115cf6315e9b3f1ed13400a2643e983967462f9578cb59b11e75192b` | 口 7：SCL PF6，SDA PF7，灯 PA8 |
| `PADUEX5_P8_V3.5.bin` | `407c80dc76219fb832c23e8063029d0fa3205c6aaf80d34d2c12491ec370a7b8` | 口 8：SCL PB10，SDA PB11，灯 PB13 |
| `PADUEX5_P9_V3.5.bin` | `0434c4529995709fe6fe38d85481499447a832324e2c1627ad20bcd95bd591ac` | 口 9：SCL PB2，SDA PA10，灯 PB12 |

每份都是 37072 字节，HVer `13`，`0x14C = 0x080084A5`。基础版本是 `PADUEX5_V3.2.bin`。V3.4 还没有合并到 main，它改的地址与这里不重叠，以后可以把构建脚本的输入换成 V3.4。

上一版只做了口 6、而且地址写死，SHA-256 是 `a145c2574f1004f336c39223d58452076b8baace869c0548db6f640ab2bb21a2`。那一版已经刷过的板子，按下面的顺序改刷本目录的新文件。

## 先刷哪一份

口 6 的脚是从初始化顺序推出来的，上一版按这个推断刷过，真机上 1～4 号口正常、6 号口没有反应。所以这一对脚的把握偏低，P7、P8 是同一推断的后两对，P9 的两根脚不在同一个 GPIO 口上、把握同样偏低。建议顺序仍是 **P6 → P7 → P8 → P9**：P6 这一版多了地址探测，若上一版没反应只是因为芯片地址不是 `0x80/0x88/0x86/0x84`，刷 P6 就能用。

## 怎么确认刷对了

1. 核对文件的 SHA-256 与上表一致。四份的上位机版本号相同。
2. 上位机「固件升级」选中文件。完成后左上角应是 `FVer=V3.5`、HVer 13（PADUEX5）。
3. 需要看报文时，GET_MODE 的回包是 `47 <mode> A2 13 03 05`。

接线：插主板后置 USB 口，不要用机箱前面板 USB 口和无源 HUB。两块板同时用、需要扩展时，用带独立供电的 HUB。

## 怎么判断这一份是不是插对的口

看调试模式里第 5 键的四条 RAW 柱（第 17～20 项），不要只看游戏有没有反应。把 5 号踏板的 8 针线插到文件名对应的口。

- 柱子随踩踏变化：就是这一份。灵敏度、颜色、改键仍在上位机的第 5 键上设置。
- 四条都停在 0：这个口的脚没有应答，换下一份。
- 四份都是 0：脚的位置可能对，但 SCL 和 SDA 反了。把 `firmware/patches/build_paduex5_px_v3.5.py` 里该口的 `scl` 和 `sda` 对调，重新构建再试。

万用表：插座上的 SCL、SDA 应分别与上表的两根脚导通，灯针与灯脚导通。

上一版在芯片不应答时会把读数换成 3915，第 5 键从上电起就是按下。游戏如果忽略「一开始就按着」的键，表现就是完全没反应，调试柱则顶在满量程。这一版在一个芯片都不应答时返回 `0xFFFF`，换算为 0，柱子停在 0，第 5 键保持松开。

## 四个口各是什么脚

固件里能坐实的只有口 5：PC11 = SCL，PC12 = SDA，灯在 PC8。板级初始化在它后面又配了四对同样的脚和四根灯脚，顺序是 PB3/PB4、PF6/PF7、PB10/PB11、PB2/PA10，灯是 PC9、PA8、PB13、PB12。先初始化的那根按口 5 的习惯当作 SCL。固件里没有 6～9 号口的地址表，这个对应是推断，所以上面让四份都试。

每份镜像在第一次采样时探测 8 位写地址，口 5 的一组优先：

```
0x80 0x88 0x86 0x84  0x82 0x8A 0x8C 0x8E  0x90 0x92 0x94 0x96  0x98 0x9A 0x9C 0x9E
```

前四个有应答的，按这个顺序放进第 5 键的四路。换算仍是 `3915 - min(raw × 0.625, 3915)`。键码、`Sensi[16..19]`、`Color[16..19]`、消抖槽位都还是第 5 键。1～4 号口的代码没有改。

## 改了哪些地址

相对 `PADUEX5_V3.2.bin`：

| 位置 | 作用 |
|---|---|
| `0x08005DE8..0x08005DFF` | 四个 6 字节入口，位于原来执行不到的区间（`0x08005DE6` 的跳转和 `0x08005E50` 都没动） |
| `0x08006F78 / 0x08006F84 / 0x08006F90 / 0x08006F9C` | 四次采样调用改为先取探测到的地址 |
| `0x0800852A..0x0800881F` 之内 | 口 5 的位操作换成带地址探测的引擎，SCL/SDA 可以不在同一个 GPIO 口。`0x08008898` 起的电源监测总线未改 |
| 第 5 键灯带 `0x080071DC / 0x080071F0 / 0x0800720C / 0x08007220` 以及端口字面量 `0x08007208 / 0x08007238` | 改到上表的灯脚 |
| `0x0800616A` | 次版本改为 5 |

原理、探测用的 RAM 地址和构建方法见 `firmware/patches/paduex5-port6.md`。

## 验证

Unicorn 执行镜像里的真实采样、扫描和刷灯，I²C 用位级从机，灯带用 GPIO 写记录。`firmware/tests/emu_port6_remap.py` 对四份镜像和 V3.2 都通过：目标口的四路按 `0x80/0x88/0x86/0x84` 换算成 3915 / 2635 / 1355 / 0，其余口没有 START；换一组地址 `0x82/0x8A/0x8E/0x94` 同样能换算并得到键码 `0x10`；一个芯片都不应答时四条 RAW 为 0、键码为 0、扫描能返回，1 号口仍能按下和松开；踩目标口灯只出现在该口的灯脚上。`emu_set_sens`、`emu_report_normal`、`emu_keymap_e2e`、`emu_keyscan_paduex4`、`emu_get_mode` 在 P6 与 P9 上通过。

用上一版镜像把总线上的器件拿掉再跑一次：键码停在 `0x10`，四条 RAW 都是 3915，扫描能返回；踩 1 号口变成 `0x11`，松开回到 `0x10`；1～4 号口的 ADC 换算仍是 `0xFFF - adc`。那 98 字节没有碰到公共扫描路径。

## 回滚

刷回 `firmware/PADUEX5_V3.2.bin`（SHA-256 `83cb64af023dfa5cc18c9ae02a6d80f849e4fa13e959716df759c5769e4ff2c8`）或以后的普通五键 V3.x，第 5 键回到 5 号口。灵敏度、颜色、消抖在这几份固件之间通用。上位机对 V3.5 的保存和升级判断与 V3.2 相同，不用换上位机。
